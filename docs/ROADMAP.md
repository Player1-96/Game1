## 零、三个方向的最终结论（一句话版）

| 方向 | 结论 | 为什么 |
| --- | --- | --- |
| **无限模式** | ✅ **第一个做** | 不卡美术、不卡设计量，复用现有 `spawnWave`，当天能玩到 |
| **风格地图** | ⚠️ **第二个做，但分 3 期** | 机制好，但「每风格分层段」导致 9 个内容包，量最大 |
| **法宝融合** | ✅ **第三做，收益最高** | 成本低、收益高，且与风格是**乘法**关系 |

风格地图卡 ~30~40 个新绘制 + 9 套色板；无限模式几乎不卡任何东西。

## 一、无限模式（无尽试炼）

### 需求（用户原话）

> 「无限模式的意思是无限刷怪的意思，就用带出来 build，然后不断刷新更强的怪，
> 然后直到打不过，看下杀了多少只怪还有存活了多久」

### 为什么它最便宜 —— 技术现状核实

| 需要的能力 | 现状 | 结论 |
| --- | --- | --- |
| 刷怪 | `spawnWave(i)`　`game.js:763` | ✅ 现成 |
| 防贴脸 | `safeSpawn(x,y,r)`　`game.js:742` | ✅ 现成（自动把怪推离玩家） |
| 妖物按层解锁 | `enemyPool(depth)`　`dungeon.js:486` | ✅ 现成，改成「按波次」即可 |
| 难度曲线 | `difficultyOf()`　`dungeon.js:40` | ⚠️ 有 `DIFF_MAX=3.0` 封顶，无限模式要**另起一条曲线** |
| 计时计分 | — | ❌ **唯一的新建** |
| 结算界面 | `state='win'/'dead'` 已有　`game.js:838/846` | ⚠️ 复用状态机，换文案与字段 |

**所以「无限模式」的真实工作量 = 一个刷怪循环 + 计时计分 + 一个结算界面。**

### 设计要点

**1. 不要只叠血量 —— 那是「血包墙」**

只加 `hpScale` 的后果：怪越来越肉但不越来越凶，玩家体感是**打得手酸**而不是**越来越紧张**。

必须叠 **3 个维度，且错开节奏**：

| 维度 | 手段 | 节奏 |
| --- | --- | --- |
| 数量 | 每波多 1~2 只 | 每波都加 |
| 种类 | 逐步解锁后期妖物（复用 `enemyPool`） | 每 3~5 波跳一档 |
| **规则（词缀）** | 「死亡分裂」「持续毒雾」「命中回血」… | **每 5 波给一个新词缀** |

**规则维度是让「无限」不无聊的关键。** 纯数量 10 波后即麻；词缀让第 30 波仍有新东西。
且**词缀是纯逻辑，零美术成本**。

**2. 与「法宝融合」挂钩（强烈建议，几乎免费）**

- 无限模式内击杀**掉落融合材料**，且**允许局内融合**
- 一举三得：① 局内成长（不只是等死）② 融合的**试错场**（正常局不敢乱融）
  ③ 结算从「杀了多少」升级为「**融出了什么**」，更有分享欲

**3. 数值曲线：另起一条，不复用 `difficultyOf`**

`difficultyOf` 的 `DIFF_MAX = 3.0` 是给 5 层制的，无限模式需要无上限曲线。
建议形式：`hpScale = pow(1.06, wave)`，并给数量/词缀各自独立的步进。
**具体系数必须先探针实测**（见 skill 的探针约定），不要凭感觉定。

**落地时新增的两条硬约束（原计划没写，是实测撞出来的）**

1. **下一波只在场面清空后才排。** 原先计时器一边打一边倒数，60 秒后场上堆到 260+ 只 ——
   不是难度是幻灯片。`endlessTick` 改成「有活口就 return」，间隔只在清场后才开始走，
   并加 `clearCooldown = 30` 帧地板防秒清秒刷。
2. **`exitEndless()` 里不能 `clearSave()`。** 原计划抄挑战模式的「不销档」，
   但收场时顺手写了 `clearSave()`（想的是「反正无尽不写档」），
   实际会把玩家的**真实通关进度删掉**。挑战模式能那么写是因为它是调试场；
   无尽要用玩家自己的档，动了就是数据事故。

### 边界条件

- **不写档、不动已有存档** —— 抄挑战模式的守卫写法：`saveGame()` 开头
  `if (this.chall || this.endless) return false;`。
  ⚠️ 挑战模式曾因为没在 `newRun()` 里清标志，导致开局存档被守卫挡掉，别重蹈。
- `newRun()` 里要清 `this.endless`。
- 复用 `state` 机制时注意：`clearSave()` 在 `dead`/`win` 里被调用，无限模式**不能销真实存档**。
- **妖物池的键必须来自 `ENEMY_DEF`**，不能混进 `ELITE_DEF` 的键
  （`xiesha`/`youyan`/`jiying`/`wandu` 是精英，`duannian` 是剑灵的精英变体）——
  写错的后果是 `new Enemy` 直接抛异常把整局打断。已加兜底 `|| 'yinsha'` 与断言。

## 二、风格地图

### 需求（用户原话，已澄清两轮）

> 「一开始肯定就是让玩家三选一先，然后后面每五层选一次二选一」
> 「我的意思是可以进入相同的风格，会出现中式-中式-中式的可能性，
> 然后每个风格 1~5 层 5~10 层 10~15 层产出的怪和法宝都不一样」

### 组合数学（已枚举验证）

允许重复选择 → **每个节点都是完整三选一**（不是二选一）：

```
3 × 3 × 3 = 27 条路径
├─ 单一风格   3 条　中中中 / 北北北 / 克克克
├─ 两风格混搭 18 条
└─ 三风格全用 6 条
```

⚠️ **这个「允许重复」有一个必须正视的后果**：

> 「中-中-中」是合法路径 → 玩家会**连着走 3 段中式**
> → 中式必须备齐 1~5 / 5~10 / 10~15 **三套内容**。

**所以「每风格分层段产出不同」不是可选项，是设计的必需条件。**
你原话里已经提到了这一点，它是整个设计的支点 —— 它把「27 条路径」塌缩成
**「3 风格 × 3 层段 = 9 个内容包」**。

### 真实成本（核实过的数字）

代码现状：普通妖物 13 种共 **1912 行**绘制代码（**均值 147 行/只**）；
Boss 5 个共 250 行（约 50 行/个）。

| 项 | 天真估算 | 说明 |
| --- | --- | --- |
| 妖物 | 54~72 种 → **约 8000~10000 行** | 3 风格 × 3 层段 × 6~8 种 |
| 法宝 | 54~72 件 | 每件还要图标 |
| Boss | 9 个 → 约 450 行 | Boss 不能用变体糊弄 |
| **合计** | **约 130 个新绘制** | 与「一次做满 3 风格 × 15 层」等价 |

**结论：27 条路径的红利（可增量扩张）被「每风格都要分层段」抵消了。**
没法只做 3 个包，因为每个风格都得有 3 段。

### 两个能把成本压到 1/4 的技巧（关键！）

**技巧 1：同一敌人复用三个层段，靠「变体」而非「新绘」**

同一个精灵改三件事 = 三个层段的敌人：

| 手段 | 成本 |
| --- | --- |
| 配色（`c1`/`c2` 换色） | **零新绘** |
| 体量（scale 1.0 → 1.15 → 1.3） | 零新绘 |
| 行为参数（`hpScale`/速度/弹幕数） | 改数值 |

→ 每风格只需 **6~8 个新绘制**，就能撑起 3 个层段的 18~24 个敌人位。
**妖物成本：54~72 → 18~24。**

**技巧 2：层段差异走「词缀」而非「新敌人」**

10~15 层的中式不该是「又一批新妖怪」，而该是
**「你已认识的妖怪，带上了金丹期词缀」**：

- 符修带「雷劫」（死亡落雷）
- 剑灵带「剑域」（周围持续伤害圈）
- 血蝠带「嗜血」（命中你回血）

**熟悉又陌生** —— 玩家不用重学敌人行为，但要重学怎么应对。
**词缀纯逻辑，零美术。**

**→ 两个技巧合用：约 130 个绘制 压到 30~40 个。**

### 「内容包」的重新定义

不要把内容包定义成「一套全新敌人」，而是：

> **内容包 = 一套色板 + 一组词缀 + 一个 Boss + 该风格专属法宝池**

于是 9 个内容包的真实成本：

| 项 | 数量 | 说明 |
| --- | --- | --- |
| 新绘敌人 | 18~24 个 | 每风格 6~8 个，靠配色撑 3 段 |
| 新绘 Boss | 9 个 | 每风格每段 1 个，**省不掉** |
| 色板 | 9 套 | 纯数据（`Style.pal`） |
| 词缀 | 27~36 条 | 纯逻辑 |
| 法宝/神器/人格碎片 | 27 件 | 每风格 9 件（3 段 × 3 件） |

### 前置技术债：`Style.pal` 可插拔（**必须先做**）

现状核实（`PAL` 是全局单例，换风格必须先把色板参数化）：

| 文件 | `PAL.` 引用 | 硬编码 hex |
| --- | --- | --- |
| `sprites.js` | **434** | 76 |
| `entities.js` | **162** | 17 |
| `game.js` | 117 | 43 |
| `items.js` | 72 | 6 |
| `skills.js` | 29 | 0 |
| `px.js` | 1（定义处） | 38 |
| `dungeon.js` | 0 | 2 |
| **合计** | **815** | **182** |

⚠️ **`sprites.js` 是重灾区（434 处 + 76 处硬编码）**，且素材是**启动时烘焙**的
（`buildSprites()` 一次性烤成 canvas 缓存）。
→ 换风格意味着**重新烘焙**，要确认性能可接受（探针实测烘焙耗时）。

**做法建议**：
1. `PAL` → `STYLE_PAL[current]`，用一个取值函数 `pal('jade')` 过渡
2. 182 处硬编码色**收敛进各自风格的色板**（这是最枯燥但必须的一步）
3. `buildSprites()` 支持按风格重建，加缓存（按风格 key 缓存，避免重复烘焙）
4. 中式作为第 1 个风格先跑通，**加断言**：`_t_styles` 补「两风格色板互不污染」

### 第 2 期的实际落地（2026-09-23 完成）

**探针实测（动手前先定案）** —— `dev/probe/_probe_pal.js`

| 项 | 实测 | 结论 |
| --- | --- | --- |
| 烘焙总耗时 | **141.7ms**（预热后 8 次中位 **121.5ms**） | 约 7 帧，**必须缓存**，否则换段会掉帧 |
| 素材体量 | 107 张 canvas / 0.23MB | 3 套缓存仅 **0.7MB**，缓存完全划算 |
| 同种子重绘一致性 | ✅ 完全一致（`mulberry32` 播种） | **缓存安全** |

**做法（与原计划一致，实现路径换成了 Proxy）**

1. **`PAL` 从单例改成 Proxy**，指向 `PAL_ACTIVE`。
   → **812 处 `PAL.xxx` 一个字没改**。这是本次最关键的工程判断：
   把「改 812 处」变成「改 1 处 + 加一层代理」，风险从「改错一处就静默配色错乱」
   降到「代理的 5 个 trap 写对就行」。
2. `STYLE_PAL` = 中式 3 段，每段 **47 键**（原 39 键 + 新收 8 键环境色）。
   `STYLE_DEF` = 3 风格（`cn` ready:true / `nordic` / `cthulhu` ready:false）。
   `palOf / curPal / setStyle / pal` 五个函数；`cn_1` 是**原版配色一字不改**，保证老存档观感一致。
3. **硬编码色 182 → 30**，按「色板分层判据」收敛（见下）。
4. `buildSprites(style, seg)` + `SPR_CACHE`（key = `style_seg`，如 `cn_0`）+ `switchStyle()`。
5. `game.js` 落 27 路径机制：`STYLE_SYS` / `segOfFloor` / `isSegPickFloor` /
   `nextFloor` 改造 / `applySegmentPalette` / `openStyleMenu` / 三选一面板与键盘 /
   顶栏风格标识 / 存档落盘与回落。

**落地时新增的两条硬约束（原计划没写，是实测撞出来的）**

1. **`setStyle()` 必须是唯一改 `PAL_ACTIVE` 的入口。**
   `buildSprites` 的「有参」与「无参」两条分支都要走它。原先无参分支直接读
   `STYLE_CUR/STYLE_SEG` 去查缓存却没调 `setStyle` —— 一旦外部已把 `PAL_ACTIVE`
   换成别的色板，就会出现「缓存的键是 `cn_2`、实际画的是 `cn_1`」这种**不报错**的错位。
   （由探针 P7 抓出来的真 bug）
2. **池里只有 1 个风格时不弹面板。**
   第一期只有中式 ready，弹「三选一」等于每次开局/每段用一个**没有任何选择的面板**
   拦玩家一下（出图才发现）。`openStyleMenu` 加 `pool.length === 1` → 直接采用、不弹面板。
   **「机制先立起来」的正确形态是：机制在，但不给玩家制造空选择。**

**色板分层的判据**（已写进 `px.js` 注释，改配色前先读）

| 类 | 处理 | 例 |
| --- | --- | --- |
| ① 环境色 | **收进色板** | 地面/墙/门/宝箱/图标底/HUD/小地图/描边 → `wall / wallHi / wallLo / rune / moss / edge / edgeSoft / edgeWarm` |
| ② 妖物固有色 | **故意不收** | 血蝠永远是红的，是辨识特征；跨风格变化走技巧 1 的 `c1`/`c2`（三期需要） |
| ③ 中性色 | **不收** | `#fff` / `#000` / `rgba(...,0.x)` 遮罩 |

**剩余 30 处是「有意的保留」**（18 处妖物固有色 + 17 处中性色，有重叠计数），不是漏网。

### 层数定案：**主玩法 15 层**（2026-09，用户拍板）

用户明确要求主玩法 **15 层**，理由是**层数与后续「法宝融合」是乘法关系**：

> 「层数不够的话养法器的空间就会比较小」

数据核实 —— 一局能养出的法宝件数约 = 层数 × 1.6：

| 层数 | 一局法宝期望 | 融合（试错 + 定型两条路）够不够 |
| --- | --- | --- |
| 9 层 | ≈ 14 件 | 刚好卡在「勉强够」，一旦误融合就报废 |
| **15 层** | **≈ 24 件** | 有富余做「先试一条路，再定型一条路」 |

**快速模式（9 层）本期不做** —— 用户决定不做，避免在主线未稳时多开一条分支。

### ⚠️ 改成 15 层必须同时解决的三个卡点

单纯把层数从 5 拉到 15 会让「名义上改了、实际不好玩」。改之前先探出三个硬卡点，
统一用 **「按段计算」** 解决（`SEG_FLOORS = 5` → `SEG_COUNT = 3` → 共 15 层）：

| # | 卡点 | 症状 | 解法 |
| --- | --- | --- | --- |
| ① | `BOSS_KEYS` 只有 5 位，原 `BOSS_KEYS[Math.min(4, depth-1)]` | 第 6~15 层**连着打 10 次烛龙** | Boss **只在段末**出现，按段取人 → 一局 3 个 Boss（第 5/10/15 层） |
| ② | `DIFF_MAX = 3.0` 在战力 12 就封顶 | 后 5 层难度**完全不动**（血包更厚而已） | `DIFF_MAX_BY_SEG = [3.0, 3.8, 4.6]`，**每段各自封顶** |
| ③ | `LOOT_DECAY = 0.82` **按层**衰减 | 15 层 = `0.82^14 ≈ 0.060` → 掉率只剩 6%，是死局不是难度 | 衰减单位改**每段一档** → `0.82^2 ≈ 0.67`，对齐原 5~6 层手感 |

**「按段」是本期所有跨层节奏的统一单位。** 三个派生量都在 `dungeon.js`：

- `segProgress(depth)` —— 段内进度 0→1（爬升形状）
- `runProgress(depth)` —— 整局进度 0→1（用于数量/密度）
- `segOf(depth)` —— 段号 0/1/2（用于解锁、封顶、取 Boss）

> **为什么判定放 `dungeon.js` 而不是 `game.js`**
> `new Floor()` 生成房间时就要按段分 Boss —— 这比 `game.js` 更早一层。
> 放 `game.js` 会形成「下层依赖上层」的倒挂（模块顶层调用即 TDZ 崩）。
> `game.js` 里的 `segOfFloor` / `isSegPickFloor` 是**转发别名，不是副本** ——
> 两边各算一次迟早会算出不同的段。

### 段末 Boss 强度：`BOSS_SEG_MUL = [1.00, 1.18, 1.36]`

按段分配 Boss 之后，「段末」成了玩家唯一的硬门槛，
所以段末 Boss **额外加厚**（用户要求「要注意强度」「段末再加一个也是好提议」）：
血魔 → 白骨 → 裂煞 逐段递增，配合 `hpBase` 的段间台阶，后期是「更凶」而不是「更肉」。

**挑战模式的连带修复**：`startChallenge` 原用 `BOSS_KEYS.indexOf(id)+1` 推层数，
「按段取人」后索引 0（血魔）会算出**第 1 层 —— 而第 1 层没有 Boss 房**，
挑战模式会开成一张没有头目的白图。改用 `bossFloorOf(id)`（该尊者所属段的段末）+
`bossOverride` 显式指定，五位尊者才都能单挑。

## 三、法宝融合

### 为什么收益最高

- 20 件两两组合 = **190 种**；三件 = 1140 种。**组合爆炸，成本却是线性的**
- 全部复用现有 `stats`，**不需要新玩法逻辑**
- 美术成本极低：融合图标可走「两图标叠合 + 描边」的**程序化生成**
- **与风格地图是乘法关系**：风格提供新材料，融合提供新连接

### ⚠️ 最大的坑：会做出「伪融合」

`stats` 系统**本身已是隐式融合**（伤害 × 射速 × 分裂，`powerScore` 里已是乘性估算）。
如果融合只是「+50% 伤害」，玩家体感就是「又一个数值法宝」，**1+1>2 的爽感完全不会出现**。

**真融合必须满足至少一条：**

| 类型 | 例 |
| --- | --- |
| **产生新机制** | 青锋剑 + 引雷符 → 飞剑命中后**原地留下持续雷电** |
| **打破原有约束** | 太虚护盾 + 羽衣 → 护盾**溢出时转化为伤害** |
| **改变行为方式** | 混元珠 + 分影诀 → 散剑**各自独立追敌** |

**判断标准：如果融合结果的说明能用「伤害 +X%」写完，它就是假的。**

### 设计约束

1. **融合必须「锁得住」**。随时可拆重融 = 没有取舍。
   需要消耗材料（比如吃掉两件 `Lv3` 法宝），选择才有重量。
2. **先做 20~25 个手写配方**，**不要**一开始就做组合爆炸。
   手写配方能保证每条都是真融合；全组合必然大量注水。
3. **融合图鉴 = 免费的 meta 层**。
   现在全局无 `achievement`/`unlock`/`meta`（已搜过），**零元进度是最大留存缺口**。
   图鉴（哪两种融过、效果是什么）存 `localStorage`，**不占资源栏**，直接补上缺口。

### 交付物清单

- [ ] `FUSION_DEF` 配方表（先 8~10 条，每条都带新机制）
- [ ] 融合判定与执行（背包里把两件拖到一起 → 确认 → 变新法宝）
- [ ] 融合图标程序化生成（两图标叠合 + 描边）
- [ ] 图鉴页（`localStorage`）
- [ ] 与无限模式联动（掉落材料 + 局内融合）
- [ ] 回归 `_t_fusion.js`（每条配方断言：生效、材料消耗、图鉴记录、不可重复融）
